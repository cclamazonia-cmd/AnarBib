### Phase 5 — Cadrage spec multi-appartenance (~17h-19h30)

Le déclencheur initial était #CL.10 (« infos pratiques de retrait intégrées au parcours »), item présenté comme simple UX dans le cahier Dunkerque. À l'examen doctrinal, on a découvert qu'il ne pouvait pas être implémenté proprement sans avoir d'abord une spec de multi-appartenance lectrice — parce que afficher la biblio de retrait n'a de sens qu'à condition qu'une lectrice puisse être membre de plusieurs biblios et qu'on sache comment articuler les contextes.

Au lieu de rédiger directement la spec en fin de journée (option refusée doctrinalement), le choix s'est porté sur un **cadrage doctrinal complet** : identifier toutes les zones d'ombre, les trancher avec Xavier, produire un document de cadrage qui servira de base à la session de rédaction ultérieure.

Le cadrage s'est déroulé en deux temps :

**Premier tour** (~17h-18h30) : 8 clusters de questions identifiés (modèle d'appartenance, contexte d'action, droits, conflits cross-biblio, identité, articulation avec specs existantes, transitions, technique). Premiers arbitrages rapides : auto-inscription lectrice, sélecteur de biblio courante, tout par biblio (rôle, restriction, cotisation), affichage agrégé sur conta. 12 zones d'ombre persistantes identifiées.

**Second tour** (~18h30-19h30) : traitement point par point des 11-13 zones restantes. Arbitrages tranchés successivement :

- A.2 — biblio principale persistée (`is_primary`).
- A.4 — sortie avec distinction suspension/résiliation, 4 sous-arbitrages (geste lectrice, résiliation définitive, durée de suspension liée à purge RGPD complète, accès lecture conservé pendant suspension).
- B.2 — persistance `sessionStorage` côté frontend, badge contextuel sur pages d'action sensible.
- D.1 — avertissement non-bloquant pour emprunt même `book_id` cross-biblio.
- E.2 — numéro lectrice par appartenance, **format libre par biblio** (respect tradition fichier papier H1 confirmée par Xavier comme condition d'adhésion), saisie staff manuelle via workflow validation physique.
- E.3 — transparence minimale par défaut + enrichissement via partenariat stabilisé déclaré entre biblios.

Audit du schéma `user_library_memberships` en cours de cadrage : surprises multiples (`is_primary` existe, `status` avec CHECK active/pending_removal/removed/inactive existe, `history_enabled` existe, 13 fonctions `fn_team_*` / `fn_network_admin_*` / `fn_cron_*` consomment `pending_removal`). Pivot doctrinal acté : posture α (enrichissement du vocabulaire existant) plutôt que refonte. 8 statuts d'appartenance au final (4 existants + 4 nouveaux). Option ρ sur `history_enabled` : la spec rétention historique livrée plus tôt prend précédence, trigger de synchronisation pour préserver `fn_export_my_data`.

Identification doctrinale majeure en fin de cadrage : **`spec-partenariat-biblios`** — nouveau chantier doctrinal nécessaire, pas une dépendance bloquante pour la rédaction de la spec multi-appartenance, mais nécessaire avant son implémentation complète. L'infrastructure UI amorce existe déjà dans la page biblio (section *Parcerias de correspondência*).

Cadrage final : 751 lignes, 23 zones d'ombre toutes traitées. Document committé dans `docs/journal/cadrages/CADRAGE_spec-multi-appartenance-lecteur_2026-05-31.md`.

## Apprentissages méthodologiques

**1. Auditer avant de coder.** Quatre faux non-acquis détectés au cours de la journée par audit `information_schema` ou recherche dans le code existant : RPC `fn_v2_book_session_availability_for_current_user` déjà existante (économise #CL.1 socle SQL) ; composants `BookAvailability` et `ContaTabHeader` déjà créés dans le projet (économise #CL.6 partiel) ; `is_primary`, `status`, `history_enabled` déjà sur `user_library_memberships` (économise la création de colonnes neuves) ; 13 fonctions `fn_team_*` consomment déjà `pending_removal` (évite de spec'er en double). Économie de travail substantielle.

**2. Spec avant code pour topics doctrinaux.** La spec rétention historique aurait été un mécanisme ad-hoc disparate sans la spec préalable. La règle gagne en stabilité : pour tout topic qui touche à des décisions doctrinales (RGPD, droits lectrice, autonomie biblio, transparence inter-biblios), précédence de la spec sur l'implémentation. La spec multi-appartenance suit la même règle — cadrée doctrinalement avant rédaction, rédaction avant implémentation.

**3. `git add` obligatoire après `Copy-Item`.** Le pre-commit hook lit `git show :file`, pas le disque. Deux faux blocages dans la journée par cette même cause. À inscrire en mémoire opérationnelle.

**4. Quatre erreurs Claude corrigées dans la journée**, toutes liées au même pattern : copier la structure d'un handler ou d'une fonction existante sans vérifier les colonnes réelles. Locales manquantes (handlers EF), syntaxe `RAISE` (PostgreSQL), doctrine GRANT scénario C (oubli REVOKE sur PUBLIC), colonne fantôme `profiles.default_library_id`. Pattern à inscrire dans la mémoire de Claude : `information_schema.columns` systématique avant tout SELECT sur une table peu familière.

**5. Doctrine « frank collaboration » appliquée plusieurs fois.** Trois freinages explicites de Claude au cours de la journée — sur tentative d'implémentation directe de #CL.8 sans spec préalable, sur tentative de cadrage rapide de multi-appartenance sans audit `information_schema` préalable, sur tentative en fin de journée de démarrer une implémentation ou une rédaction de spec en bout de fatigue. Les trois freinages acceptés par Xavier, qualité de la session préservée.

## Notes pour le GLB v18

Au moment où le GLB v18 sera rédigé (cadence lente, pas avant fin juillet selon doctrine), trois axes structurants émergent de cette session :

1. **Trois doctrines lectrice** posées en moins de 12h — c'est une densité doctrinale qui mérite un chapitre dédié au GLB, articulé sur le triptyque autonomie lectrice / souveraineté biblio / mémoire collective non-occulte.

C'est un mouvement intéressant à documenter : comment la confrontation à une question concrète (transparence inter-biblios sur une lectrice multi-biblio) a fait émerger la nécessité d'un dispositif doctrinal général (le partenariat stabilisé) qui régira toute une famille de questions futures.

3. **La méthode du cadrage doctrinal complet préalable à la rédaction de spec**. Inaugurée pour multi-appartenance, elle pose un troisième palier entre l'idée brute et la spec rédigée : cadrer toutes les zones d'ombre, les trancher avec arbitrage explicite, produire un document de cadrage avant rédaction. Méthode à inscrire au GLB comme pratique transférable.
